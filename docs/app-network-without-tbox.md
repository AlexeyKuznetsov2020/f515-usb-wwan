# Мобильный интернет приложениям без правки TBOX-сети

> 2026-08-14. Ответ на вопрос: «можно ли раздать интернет приложениям Android, **не трогая
> призрачную TBOX-сеть** (`vlan72`) — без `ip route … table vlan72` и без DNAT DNS `192.168.72.1`?»
>
> Коротко: **для собственного трафика головы** (root/adb/системные демоны) TBOX и так не нужен —
> он идёт через `table main` (см. [app-network.md](app-network.md)). **Для приложений Android**
> единственный полный и не-привилегированный по маршрутизации путь без правки `vlan72` — это
> **VpnService**. «Правильный» путь через `NetworkAgent`/Ethernet требует платформенной подписи и
> на этой заводской `user`-прошивке недоступен — именно поэтому нынешнее приложение и правит
> таблицу маршрутов.

## Почему приложениям сейчас нужен TBOX-хак

- **root/adb/системные демоны** маршрутизируются по `ip rule 9999: from all lookup main` (вендор
  держит его раньше любых fwmark-правил). `ip route replace default dev <wan> table main` — и всё.
  TBOX тут ни при чём.
- **Приложения** `ConnectivityService` заворачивает fwmark'ом в таблицу КОНКРЕТНОЙ сети
  (`ip rule` prio 13000/14000 → `lookup vlan72`), `main` для них не участвует. Единственная сеть
  с `CELLULAR/INTERNET` (когда Wi-Fi выключен) — призрачная TBOX (`vlan72`) с мёртвым шлюзом
  `192.168.72.1`. Отсюда правка `table vlan72` + DNAT её DNS. Это и есть «манипуляция TBOX-сетью».

## Варианты БЕЗ правки TBOX-сети (только для приложений)

| # | Подход | Трогает TBOX? | Права | Покрытие | Вывод |
|---|---|---|---|---|---|
| 1 | **VpnService (tun0)** + пользовательский форвардер в модем | **Нет** | не нужны для маршрутизации (только согласие на VPN) | все приложения | **Рекомендую** |
| 2 | Зарегистрировать реальную сеть (`NetworkAgent` / Ethernet `config_ethernet_iface_regex`) | Нет | **платформенная подпись / system UID / CONNECTIVITY** | все, нативно | «Правильно», но **заблокировано** на locked-прошивке |
| 3 | Маршрутизация по UID (`ip rule add uidrange … lookup <modem_table> prio 12000`) | таблицу `vlan72` не трогает, но DNS `192.168.72.1` всё равно мёртв → нужна отдельная правка DNS | root | все приложения | Частично; хрупче #1 |
| 4 | Системный `http_proxy` на модем | Нет | root | только HTTP(S)-приложения, знающие прокси | Неполно |

## Вариант 1 — VpnService (конкретно)

`VpnService` заставляет Android заворачивать трафик всех приложений в `tun0` СВОИМИ правилами —
независимо от таблицы `vlan72`. Ни правок маршрутов, ни `iptables` DNAT, и вообще нет зависимости
от хрупкой призрачной сети.

```
[приложения] → tun0  (VpnService.Builder: addAddress 10.0.0.2/32, addRoute 0.0.0.0/0,
                       addDnsServer <DNS-модема>)
            → читаем IP-пакеты из tun (ParcelFileDescriptor)
            → пользовательский NAT/форвардер (tun2socks / hev-socks5-tunnel / badvpn-tun2socks)
            → локальный SOCKS/релей, привязанный к интерфейсу модема (ppp0/wwan0)
              через protect()-нутый сокет
            → модем → интернет
```

Что важно в реализации:

- `VpnService.protect(fd)` на исходящем (upstream) сокете — иначе его пакеты снова попадут в VPN
  и получится петля.
- Привязка upstream к модему: `SO_BINDTODEVICE ppp0/wwan0` либо src-маршрут через модемную
  таблицу. Модемный `default` в `table main` (его приложение уже кладёт) этот трафик и понесёт.
- DNS: отдаём приложениям рабочий резолвер через `addDnsServer(...)` (DNS модема) — мёртвый
  `192.168.72.1` вообще не используется, **DNAT не нужен**.
- Цена: копирование пакетов в userspace (просадка скорости/CPU против ядерных маршрутов), разовое
  окно согласия + иконка «ключ» VPN в статус-баре; можно сделать always-on.
- Root всё равно нужен в других местах приложения (`insmod`, `pppd`, `table main`), поэтому VPN не
  делает приложение целиком бесрутовым — он лишь убирает **манипуляцию TBOX** на пути приложений.

Готовые кирпичи для форвардера: `hev-socks5-tunnel` или `badvpn-tun2socks` (tun→SOCKS) +
любой маленький SOCKS/релей, привязанный к `ppp0/wwan0`. Кросс-компиляция под aarch64, кладётся
рядом со скриптами и запускается из стадии, аналогичной нынешней `--system`.

## Вариант 2 — почему не «правильный» путь

Добавить `wwan0`/`ppp0` в Ethernet-фреймворк (`config_ethernet_iface_regex`) или зарегистрировать
`NetworkAgent` — и приложения привязывались бы к модему нативно, как к Wi-Fi, без правок маршрутов.
Но обоим нужна платформенная подпись / system-UID / `CONNECTIVITY_INTERNAL`, которых у приложения,
установленного через Toolbox на заводской `user`-сборке, нет. Именно поэтому нынешнее приложение и
правит таблицу маршрутов. Без более глубокой интеграции в систему — недоступно.

## Важно: перезапуск system_server на загрузке — это ОТДЕЛЬНАЯ проблема (и её виновник — это приложение)

На этой голове наблюдается разовый перезапуск `system_server` на загрузке
(`sys.system_server.start_count=2`): необработанный `DeadSystemException` в потоке **NetworkPolicy**
над призрачной SIM-less TBOX-сетью. **Живой тест перезагрузками 2026-08-14 доказал, что триггер —
именно подъём модема этим приложением** (не правка маршрутов — та идёт позже и невиновна):

- автозапуск **выключен** → ребут → `start_count=1`, фатала NetworkPolicy нет, предупреждений
  «without subscriber» ноль, хотя призрачная TBOX-сеть на месте ⇒ одной TBOX-сети НЕ достаточно;
- автозапуск включён, но модем поднялся **позже** → тоже без перезапуска ⇒ это **гонка по времени**:
  падает, только если `insmod`/энумерация модема попадает в раннее окно NetworkPolicy у system_server.

**Как чинить (без пересборки APK):** поднимать модем ПОЗЖЕ этого окна. В `scripts/wwan-boot.sh`
`BOOT_DELAY` сейчас 5 с (был уменьшен с 45 с) — вернуть ближе к ~45 с, либо вместо фиксированной
паузы дождаться, пока `dumpsys connectivity` покажет устоявшуюся default-сеть, и только потом
`insmod`/modeswitch. Переход приложений на VpnService этот перезапуск НЕ устраняет (энумерацию
модема он не отменяет). Полный разбор — в репозитории Алексея:
`spec/106-system-server-restart-phantom-tbox-network.md` (§6).

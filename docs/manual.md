# Ручной запуск и технические детали

Этот файл — для тех, кому не подходит приложение (нет возможности установить, или нужен
именно ADB напрямую). Обычному пользователю он не нужен — см. [README.md](../README.md).

## Ручной запуск по ADB (без приложения)

```bash
adb shell mkdir -p /data/local/tmp/wwan
adb push scripts/wwan-up.sh scripts/wwan-boot.sh scripts/dial.sh scripts/at.sh \
         scripts/format-sdcard.sh \
         modules/prebuilt/usbserialmerged2.ko modules/prebuilt/ppp_async.ko \
         modules/prebuilt/cdc-wdm.ko modules/prebuilt/cdc_ncm.ko \
         modules/prebuilt/huawei_cdc_ncm.ko \
         tools/huawei-modeswitch \
         /data/local/tmp/wwan/
adb shell chmod 755 /data/local/tmp/wwan/*.sh /data/local/tmp/wwan/huawei-modeswitch

adb shell /data/local/tmp/wwan/wwan-up.sh --check     # диагностика, ничего не меняет
adb shell /data/local/tmp/wwan/wwan-up.sh             # подъём
adb shell /data/local/tmp/wwan/wwan-up.sh --system    # + интернет приложениям
```

Для HiLink-модема (ZTE и другие CDC-Ethernet) больше ничего не нужно. Для PPP-модема
(Huawei) заранее проверь APN оператора — без него дозвон не пройдёт:

```bash
adb shell WWAN_APN=internet.beeline.kz /data/local/tmp/wwan/wwan-up.sh --system
```

Постоянные настройки удобнее положить в `/data/local/tmp/wwan.conf` — см.
`scripts/wwan.conf.example`.

## Как это устроено

`scripts/wwan-up.sh` сначала **сам определяет тип модема**: если в системе появился
USB-сетевой интерфейс (`cdc_ether`/`rndis_host`/`cdc_ncm`/`huawei_cdc_ncm`) — это HiLink,
идём коротким путём; если
на шине висит `12d1:*` — это Huawei, идём длинным. Принудительно тип задаётся
`WWAN_MODE=hilink|ppp`. Если не нашлось ни того, ни другого, скрипт печатает дамп
`lsusb`/интерфейсов и останавливается.

Дальше он идёт стадиями. **Каждая стадия сначала проверяет, что нужно сделать именно
сейчас**: если условие уже выполнено — стадия пропускается, если нет предпосылок для
следующего шага — скрипт останавливается с понятным сообщением и подсказкой, что делать,
а не падает где-то в середине с непонятной ошибкой. Повторный запуск всегда безопасен
(идемпотентно): можно жать «Включить» сколько угодно раз, в том числе на уже поднятой
сети.

До определения типа идут две общие стадии: **режим модема** (Huawei приходит на шину
виртуальным CD-ROM'ом, переключается SCSI-командой) и **NCM-интерфейс Huawei** (см. ниже).

HiLink-ветка: поднять интерфейс → дождаться carrier → `udhcpc` → адрес/шлюз → маршруты.
PPP-ветка: файлы → модуль usbserial → последовательные порты → PPP в ядре →
SIM/регистрация → дозвон pppd → маршруты. Общий хвост у обеих веток один: маршрут в
служебную таблицу 99, проверка связи и (по `--system`) раздача интернета приложениям.

### NCM-модемы Huawei (E8278 и родня)

Часть Huawei с HiLink-прошивкой отдаёт канал данных не AT/PPP-портом, а NCM-интерфейсом,
спрятанным за vendor-specific классом `ff/02/16`. Ни `cdc_ncm`, ни `huawei_cdc_ncm`, ни
`cdc-wdm` в ядре головы не собраны, зато собран каркас `usbnet` — поэтому три драйвера
довозятся модулями так же, как `usbserial` для PPP-ветки. Стадия «NCM-интерфейс Huawei»
грузит их и, если NCM-интерфейс успел забрать `option` (он матчит всё устройство
`12d1:1506` целиком), передаёт интерфейс правильному драйверу:

```sh
printf %s 4-1:1.1 > /sys/bus/usb/drivers/option/unbind
printf %s 4-1:1.1 > /sys/bus/usb/drivers/huawei_cdc_ncm/bind
```

После этого появляется `wwan0`, и модем идёт дальше как обычный HiLink — DHCP и маршруты.
Разбор конкретного случая (Huawei E8278), со сборкой модулей и проверками перед
`insmod`, — в [ncm-e8278.md](ncm-e8278.md).

`--check` прогоняет все проверки в режиме «только посмотреть», ничего не меняя на
устройстве — полезно как первый шаг диагностики.

### Почему PPP-ветка такая длинная

Ядро головы не поддерживает Huawei «из коробки» (`CONFIG_USB_SERIAL` не собран) и не
собран line discipline для PPP (`CONFIG_PPP_ASYNC`). Модули для обоих собраны отдельно —
см. [modules/README.md](../modules/README.md), если нужно пересобрать под другое ядро.
Собирать их нужно тем же тулчейном, что и ядро (clang + ThinLTO + CFI): при сборке gcc
модуль грузится, но `module_init()` не вызывается никогда — из-за поля `cfi_check` в
`struct module` смещения разъезжаются.

Модем в USB попадает в storage-режиме (`14fe` и т.п.) и не отдаёт AT/PPP-порты, пока его
не переключить одной SCSI-командой (то же самое, что делает `usb_modeswitch`, но без
самого `usb_modeswitch`, которого на голове нет) — см. [tools/README.md](../tools/README.md).

`--system` дополнительно донастраивает маршрутизацию так, чтобы интернет через модем
видели не только root/adb-команды, но и обычные приложения Android — в том числе когда
Wi-Fi выключен и никакой другой сети нет. Детали — в [app-network.md](app-network.md).

## Ограничения

- `insmod` (только PPP-ветка) — единственная операция, способная уронить ядро головы.
  `rmmod` не делается никогда: выгрузка этих модулей роняет ядро гарантированно.
- Если модем физически вынуть и вставить снова, режим `14fe` возвращается — `wwan-up.sh`
  сам это увидит и вызовет modeswitch заново.
- `/` на этой прошивке read-only (dm-verity) — всё, что делает скрипт, это runtime-
  состояние ядра/сети, ничего не пишется на системный раздел. После перезагрузки всё
  поднимается заново: либо кнопкой, либо автозапуском ([autostart.md](autostart.md)).
